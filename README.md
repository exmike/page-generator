# page-generator

Библиотека-кодогенератор Page Object'ов для UI-автотестов. Это **annotation processor** (`javax.annotation.processing`), который на этапе компиляции читает ваши классы-страницы и классы-виджеты, помеченные аннотациями, и генерирует по ним готовые Page Object'ы со степами Allure.

- Ветка `2.0.0-playwright` (текущая) — генерирует код под **Playwright** (`com.microsoft.playwright`).
- Ветка `master` — генерирует код под **Selenide / Appium** (`selenide-appium`).

Отличия между ветками — только в целевом фреймворке и форме генерируемого кода; сам механизм обработки аннотаций одинаковый. Подробнее см. раздел [«master vs playwright»](#master-vs-playwright).

---

## Как это работает

Обработка идёт в **два раунда** (`PageProcessor`, `SupportedSourceVersion = RELEASE_21`):

**Раунд 1 — `generatePages()`**
1. `ElementCollector` — собирает все классы-виджеты `@Element`, доливает в каждый методы из `@BaseElement`, проверяет что у методов есть `@Action`.
2. `PageCollector` — собирает все классы-страницы `@PageObject`, вытаскивает их поля-локаторы (`Locator` / `FrameLocator`), проверяет что у каждого есть `@PageElement`.
3. `MethodGenerator` — для каждой страницы генерирует методы: по одному на каждый `@Action` подходящего виджета, геттеры полей, и методы инициализации вложенных виджетов.
4. `ClassGenerator` + `SpecsCreator` — собирают итоговый `TypeSpec` и пишут `.java` через **JavaPoet** в пакет `page.generated`.

**Раунд 2 — `generateScreenManager()`**
Сканирует сгенерированные классы (помеченные `@AutoGenerated`) и собирает класс `ScreenManager` — единую точку входа с методом-аксессором на каждый экран.

Весь генерируемый код кладётся в пакет **`page.generated`**.

## Аннотации (DSL)

| Аннотация | На чём | Назначение |
|-----------|--------|------------|
| `@Element("название")` | класс-виджет | Обёртка над `Locator`. Публичные методы с `@Action` становятся степами. |
| `@BaseElement` | ровно один абстрактный виджет | Его методы наследуются во все `@Element`, у которых есть суперкласс (не `Object`). |
| `@Action("текст степа")` | метод виджета | Текст Allure-степа. Плейсхолдер `<...>` заменяется на «тип элемента + имя поля». |
| `@PageObject` | класс-страница | Экран/виджет с полями-локаторами. |
| `@PageElement("название")` | поле-локатор в `@PageObject` | Человекочитаемое имя элемента (подставляется в текст степа). |
| `@AutoGenerated` | (ставится генератором) | Маркер сгенерированных классов; используется в раунде 2. |

> `@BasePageObject` объявлен, но в текущей ветке не используется.

## Пример использования

Виджеты (`@Element`):

```java
@annotation.BaseElement
public abstract class BaseElement {
    protected Locator element;
    protected BaseElement(Locator element) { this.element = element; }

    @Action("Проверяем, что <elementName> отображается")
    public BaseElement checkVisible() { element.isVisible(); return this; }
}

@Element("кнопка")
public class Button extends BaseElement {
    public Button(Locator element) { super(element); }

    @Action("Нажимаем на <elementName>")
    public void click() { element.click(); }
}
```

Страница (`@PageObject`):

```java
@PageObject
public class LoginScreen {
    private Page page;
    public LoginScreen(Page page) { this.page = page; }

    @PageElement("кнопка входа")
    private Locator loginButton;

    // getPage() и getLoginButton() — обязательны (см. ниже)
}
```

Сгенерируется `page.generated.LoginScreenGen extends LoginScreen` с методами вида
`loginButton_click()` (с `@Step("Нажимаем на кнопка кнопка входа")`, возвращает `this` — fluent),
`loginButton_get()`, а также запись в `ScreenManager`.

### Требования к вашему `@PageObject`-классу

Генерируемый `XxxGen` **наследуется** от вашего класса и вызывает `super`, поэтому класс-страница обязан:

- иметь конструктор `(com.microsoft.playwright.Page page)`;
- предоставлять `getPage()`;
- предоставлять геттер на каждое поле-локатор (`getLoginButton()` и т.п.);
- **не быть `final`** (иначе наследование не скомпилируется).

## Соглашения по именованию (важно)

Поведение завязано на подстроки в именах (magic strings):

- метод/класс со словом **`widget`** в имени трактуется как вложенный виджет (инициализируется внутри страницы), а **не** попадает в `ScreenManager`;
- методы со словом **`getCollection`** пропускают проверку на `@Action`.

## Подключение в проект

### Java + Maven

```xml
<dependency>
    <groupId>io.github.exmike</groupId>
    <artifactId>page-generator</artifactId>
    <version>2.1.3-playwright</version>
</dependency>
```

Процессор регистрируется автоматически через `@AutoService` (`META-INF/services`). Отдельно указывать `annotationProcessorPaths` обычно не требуется, но при строгой конфигурации компилятора — добавьте туда этот артефакт.

### Kotlin

Сам генератор менять не нужно — он language-agnostic и генерирует `.java`. Работа только в сборке потребителя:

- Если классы `@PageObject` / `@Element` остаются на **Java** — работает без изменений.
- Если они пишутся на **Kotlin**:
  - использовать **kapt** (не KSP — процессор на `javax.*`, KSP его не запустит);
  - аннотации на свойствах ставить с use-site target: `@field:PageElement("...")` (иначе аннотация уедет на геттер);
  - классы-страницы делать `open` (Kotlin-классы `final` по умолчанию, а `XxxGen` их наследует);
  - плюс: Kotlin-свойства сами дают геттеры `getX()`, которых требует генератор.

## master vs playwright

| | `master` (Selenide/Appium) | `2.0.0-playwright` |
|---|---|---|
| Целевой фреймворк | `selenide-appium` | `com.microsoft.playwright` |
| Инициализация экрана | `Selenide.page(X.class)` | `new XGen(page)` |
| Генерируемый класс | одноимённый, самостоятельный | `XGen extends X` с конструктором `(Page)` |
| Тип поля-локатора | Selenide-элементы | `Locator` / `FrameLocator` |
| Ожидания (`timeout`) | генерировались `waitElement` | вырезаны |

В обеих ветках **нет кода, специфичного для Kotlin** — генератор одинаково работает с Java- и Kotlin-потребителями на условиях выше.

## Известные слабые места и техдолг

Список к разбору (примерно по приоритету):

- [ ] **Мёртвый импорт-баг.** `util/Utils.java:15` — `import jdk.jshell.execution.Util;` — случайный автоимпорт внутреннего JDK-модуля, ни на что не ссылается. Убрать (риск на модульном рантайме / строгой сборке).
- [ ] **Нет юнит-тестов.** В `src/test` лежат только фикстуры-примеры, реальных тестов нет (`PageProcessor`: `todo — написать юнит-тесты`). Для кодогенератора регрессии молчаливы → добавить компиляционные тесты (напр. `google-compile-testing`).
- [ ] **Magic strings в логике.** Поведение завязано на подстроки в именах: `"widget"` (`MethodGeneratorImpl`, `ScreenManagerGeneratorImpl`), `"getCollection"` и `"wait"` (`Utils`). Хрупко — переименование тихо ломает генерацию. Заменить на явную аннотацию (напр. `@Widget`).
- [ ] **Требования к `@PageObject` не валидируются.** Генерируемый `XxxGen extends Xxx` вызывает `super.getPage()` / `super.getXxx()`. При отсутствии геттеров/конструктора/`open` падение происходит на компиляции сгенерированного кода с невнятной ошибкой. Проверять в `PageCollector` и кидать человекочитаемое сообщение.
- [ ] **`Collector` — синглтон со статическим состоянием** (`getInstance()`). Риск утечки состояния между раундами / инкрементальной компиляцией, мешает тестам. Прокинуть экземпляр через конструктор (как остальные зависимости).
- [ ] **Смешение языков в ошибках.** Часть сообщений на русском, часть на английском — привести к одному языку.
- [ ] **История ветки не причёсана.** `2.0.0-playwright` — 30+ коммитов `fixes`/`wip`. Перед мержем в `master` сквошнуть и прогнать ревью.
